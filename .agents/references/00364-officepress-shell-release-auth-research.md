## About version selection and instructions

SemVer compares numeric version parts, orders prereleases below the corresponding release and excludes build metadata from precedence. It does not establish compatibility for a particular app migration. GitHub's latest-release endpoint chooses a non-draft, non-prerelease release using `created_at`, which reflects the release commit rather than publication time. It is not a general compatible-version resolver. [SemVer 2.0.0](https://semver.org/), [GitHub release API](https://docs.github.com/en/rest/releases/releases#get-the-latest-release).

**Historical resolver proposal, narrowed by D-12:** evaluate app identity, installed version, channel, target version, installation method, runtime requirements and migration/guide availability. D-12 keeps version/source selection but replaces app-authored guide resolution with faithful display of the release publisher’s “Upgrade Instructions”; installation applicability stays in those notes. Test 1.9 versus 1.10, equal precedence with different build metadata, prerelease opt-in, malformed versions, lower versions and unavailable migration paths. A release can be newer yet have no compatible guide. Keep installed state, available release and guide resolution separate; show a useful unavailable reason without inventing shell commands.

Conditional GitHub requests can use ETag/Last-Modified and return 304. TUF distinguishes stale/expired metadata and rollback to an older trusted metadata version. These are useful review concepts; neither a timestamp nor an ETag authenticates a release publisher. [REST polling practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api), [TUF specification 1.0.36](https://theupdateframework.github.io/specification/v1.0.36/).

Proposed release fixture fields: app ID, installed/target versions, channel, installation method, generation/expiry/check times, compatibility ranges, guide revision and trusted-source identity. Cache successful data separately from the last attempted check. Exercise timeout, invalid JSON, oversized response, stale cache, 304, rate limiting and a removed target. Use configured sources; never accept an arbitrary browser-supplied fetch URL or render unsanitized release HTML. Decide production feed/trust policy in G-03/G-18.

Upgrade guides remain informational. Earlier authoring guidance called for a tested source-to-target path, backup and restore prerequisites, dependency install, generation versus migration distinction, build/restart, verification and rollback limits. Under D-12 these are concerns for release authors, not steps for the app to generate or add to the notes. `npm ci` requires a matching lockfile and does not update it; `pg_restore` reconstructs supported archive formats created by `pg_dump`. Neither is a universal app upgrade/rollback recipe. [npm ci](https://docs.npmjs.com/cli/v11/commands/npm-ci/), [PostgreSQL 17 restore](https://www.postgresql.org/docs/17/app-pgrestore.html).

Do not promise an old binary can run after an irreversible migration. The original proposal included unavailable guidance for unsupported paths and a disposable fixture recipe. D-12 instead requires faithful display of the release-authored section and an unavailable state for missing content; no recipe execution is required for this display proof. No About button executes commands or changes a real database. Full TUF infrastructure and production deployment automation were excluded from this research scope.

## Panels and keyboard behavior

WAI's modal-dialog pattern covers focus containment, Escape and returning focus; a modal makes background content unavailable. Its window-splitter pattern describes keyboard resizing and separator values, but explicitly notes incomplete task-force review/example work. Treat it as guidance, not proof of an accessible library implementation. [Modal dialog](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/), [window splitter](https://www.w3.org/WAI/ARIA/apg/patterns/windowsplitter/).

**Proposed shell state model:** distinguish docked desktop navigation/details from a modal mobile sheet. The original research allowed one active modal layer or explicitly tested stacking. The later [D-20 decision](../specs/00001-reusable-app-shell-and-component-proofs/decisions.md) selects one mobile navigation/agent/details overlay at a time; opening another replaces it. Do not mark desktop docked asides modal. Record the opener and restore a valid focus target after close/route changes; closing the top layer must not unexpectedly close the whole app. Preserve accepted widths. Resizable panels are optional scope, not implied by researching splitters.

WCAG 2.2 requires a non-drag single-pointer alternative where applicable; keyboard support alone does not satisfy that particular criterion. Focus must not be entirely obscured by authored content under its minimum criterion. [WCAG 2.2 changes](https://www.w3.org/WAI/standards-guidelines/wcag/new-in-22/).

Proposed cases: move-card/move-question buttons plus keyboard controls, 390 px mobile, zoom/reflow, long content, both side regions available, browser back, removed opener, route change with open sheet and focus near fixed headers/footers. G-12 still owns the mobile header geometry conflict; accessibility standards do not decide OfficePress visual dimensions.

## Theme initialization and verification

CSS `color-scheme` informs browser-rendered controls; it does not substitute for application tokens. `localStorage` is origin-scoped and can throw when storage is disallowed. React expects hydrated markup to match server output. [Color scheme](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/color-scheme), [local storage](https://developer.mozilla.org/en-US/docs/Web/API/Window/localStorage), [React hydration](https://react.dev/reference/react-dom/client/hydrateRoot).

CSP can permit a specific initialization script by nonce or hash; a nonce must be unpredictable and change for each response. [CSP](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CSP).

**Proposed proof:** retain `op-mode`/`data-mode`, validate saved values, catch unavailable storage and establish mode before paint without broadly permitting inline code. Align the server shell and hydrated tree; do not suppress arbitrary mismatch warnings. Distinguish app theme overrides from a person's mode preference and explicitly decide multi-app key scope. Test reload, storage denial, corrupt preference, separate origins, cross-tab behavior and CSP-enabled built output. The subsequent [D-10 decision](../specs/00001-reusable-app-shell-and-component-proofs/decisions.md) selects one company per proof installation. App theme storage and mode-preference key scope remain in G-09; the research does not establish their implementation.

WCAG text contrast uses 4.5:1 for ordinary text and 3:1 for qualifying large text, with defined exceptions. Forced colors can remove shadows; reduced-motion preferences can require alternate transitions. [Contrast guidance](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html), [forced colors](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/forced-colors), [reduced motion](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/At-rules/@media/prefers-reduced-motion).

Test all four families in both modes, derived token pairs, focus, disabled/error/pending states, authentication and settings. Automated accessibility scans cannot find every problem; combine them with keyboard/focus/announcement inspection and human visual review. Browser fake clocks can control page time, but do not control a backend worker's clock. [Playwright accessibility limits](https://playwright.dev/docs/accessibility-testing), [clock API](https://playwright.dev/docs/clock). These are future proof methods, not tests run during research.

## Built-in authentication and sensitive account operations

OWASP distinguishes reauthentication for sensitive actions, password-reset token lifecycle and CSRF defenses. Reset requests should avoid revealing whether an account exists; tokens need limited lifetime and single-use handling. SameSite cookies are defense in depth, not a general replacement for CSRF validation. [Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), [password reset](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html), [CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

**Proposed handler tests:** challenge expiry, replay, wrong account, expired session, CSRF rejection, direct endpoint denial, password change, TOTP removal, export scope and distinct purge/delete scope. Retain submitted safe field values and accessible errors without exposing secrets. Verify actual locked Stackpress behavior; a source route name cannot prove these protections. Failed cases become adapter/framework work or explicit unsupported behavior, not cosmetic success screens.

RFC 6238 requires rejecting reuse of a successfully validated OTP and discusses bounded clock drift. This makes simultaneous submissions and restart persistence relevant tests. [TOTP RFC 6238](https://www.rfc-editor.org/rfc/rfc6238.html).

OWASP treats lost-factor recovery as a security-sensitive flow. [MFA recovery](https://cheatsheetseries.owasp.org/cheatsheets/Multifactor_Authentication_Cheat_Sheet.html). OfficePress excludes SMS, recovery codes and security keys; this source does not override that decision. The later D-21 decision explicitly excludes custom lost-authenticator recovery from the initial proof; production recovery policy remains outside that scope. Built-in reauthentication/revocation verification remains separate. D-22 recovers the accepted kit’s current-app user-data purge versus across-app account deletion scope; actual handler/data coverage still needs proof. These remain production requirements, and research does not demote them to proposals.

D-11 accepts a live source plus local fixtures; it does not choose GitHub or a manifest host. The current [GitHub Releases API](https://docs.github.com/en/rest/releases/releases) provides published release metadata, including tag names, release notes and assets; the repository remote alone does not select a feed for these proof apps. No project release inventory or endpoint compatibility was proved.

Its proposed app-owned fields can map installed/target versions to compatibility requirements and upgrade guides. That recommendation was not selected: the subsequent Q-005a answer accepts GitHub Releases under D-12. The endpoint and maintainer must be identified before a live test, and creating or publishing a feed is separate work.

## GitHub release-note authority — 2026-10-05

D-12 selects GitHub Releases and the exact heading “Upgrade Instructions”; each release supplies that content. The [GitHub release API](https://docs.github.com/en/rest/releases/releases) exposes the authored notes in `body`, verified as documentation only. Fetching and extracting a real configured app release remains P-01 work. Faithful section display supersedes custom manifest and generated-guide proposals above. Preserve the authored section and safe Markdown presentation, with source/release correlation and exact copy checks; never execute note content. Missing content remains unavailable. Release selection, cache freshness and extraction boundaries need proof cases, not inferred new upgrade commands.
