# Component proof contracts

Status: Planned / Not implemented

Each proof composes the shell and its own responsibility-owned plugin(s). Proposed persistence/error handling below must be resolved before Freeze. Use [shared app behavior](../../context/shared-app-experience.md), [source templates](../../references/00359-officepress-ui-source-resources.md) and current design records. Do not build an entire named OfficePress product as a side effect.

## C-01 Workflows and Automations

Original target: `proofs/workflows-automations/`; implemented in the combined common-components proof. Human actors: workflow designer/admin and operator. Entities: mutable Workflow with Draft/Published status, Stage, Card, Task, Transition, AutomationDefinition and AutomationRun; reuse cross-proof contracts instead of duplicating unrelated data models. D-23 supersedes WorkflowRevision and the earlier guarded-transition design.

Start with a workflow list; open a selected board without a workflow selector/count group. Demonstrate configurable stages with multiple Assignees, outcome, elapsed time target and Tasks. Workflows have no published versions; Draft/Published is saved in the workflow form. Move cards to any current column through drag or an accessible details selector. Remove WIP limits, allowed-next-stage lists and owner/task/document entry prerequisites from UI, types and backend enforcement. Reject unknown/cross-workflow destinations, unauthorized requests and stale writes. Task progress, due/SLA state, comments/files indicators and activity remain persistent. Stage Automations keeps its context/title below the action row and removes statistics and search. D-24 adds avatar-only cards, live SLA bars from stage entry to expiry, direct stage-settings cogs, centered stage headers and clickable Automations with draft preservation after task removal. Preserve legacy single-owner payloads through compatibility reads.

Automation builder covers trigger, all/any conditions, timing (now/delay/date/SLA), ordered actions and run settings; show a plain-language summary and a non-mutating test against a real fixture card. Enabling and disabling a definition is distinct from disabling the automation plugin. Lists show health, runs/failures and last outcome.

Use a fake clock and deterministic action adapters to verify delayed/SLA execution, ordering, failure records, retry/idempotency and restart behavior. Missing action/provider fails visibly without pretending completion. Disabling automations leaves board/designer functionality intact; missing a required workflow service prevents automation registration. D-26 supersedes D-15's automation publishing: save Draft/Active/Paused directly. In-progress (including waiting) and completed runs retain their original definition snapshot. Prove that edits/restart preserve accepted work while future events use the latest active definition. Both once-per-visit and stop-on-failure settings are functional. D-18 excludes email example-send retry and delivery reconciliation; G-11 retains implementation evidence. Read [round 7](../../../proofs/common-components/tests/evidence/reviews/r007-card-event-automations/notes.md) for the exact event/condition/action catalogue, conditional stage forms, layout changes and bounded message-provider implementation.

Expected signal: saved definition and actual transition/run state match; the dry run changes no business data; duplicate trigger/retry produces the agreed single effect; the independent board survives automation removal. No full distributed job scheduler is assumed. If the proof exercises an email action, D-08 requires a bounded real SMTP send to a designated test account, with the send-call result under D-18; dry run still never sends. Internal retry fixtures do not add SMTP retry or downstream delivery requirements.

D-25 requires current-stage tasks in the backend and UI, including existing cards after task definitions change. Removed tasks cannot leave stale checkboxes or counts; empty checklists have no progress count. Card title replaces REQUEST/ID and the grip sits to its left. [Round 6](../../../proofs/common-components/tests/evidence/reviews/r006-dynamic-stage-tasks/notes.md) records stable identities, completion preservation, compatibility and atomic reconciliation as proof implementation choices.

## C-02 Message Templates

Target: `proofs/message-templates/`. Human actors: template author/admin and operator preparing a message. Candidate entities: TemplateRevision, channel format, variable definitions and a render/dispatch result.

Detect `{{mustache}}` placeholders; distinguish Automatic values from record context and Custom values requested at use time. Email has subject and rich body; plain-text channels have character counts and channel-specific formatting. Preview resolves a known record, shows missing values clearly and renders malicious markup safely. Do not treat a preview as a delivery receipt.

Create, edit, validate, preview and reuse a template after restart. Required custom values block dispatch until supplied. Unknown variables, forbidden fields, wrong channel, empty subject where required and renderer errors have explicit results. Sanitize rich output and escape plain substitutions according to the destination. D-15 requires a new immutable published revision for new work; sent messages retain their original template revision and meaning. Prove that publishing a changed template leaves a prior sent message and its payload/history intact after restart, while a new message uses the new revision. Exact persistence details remain G-11 proof work.

Demonstrate an explicit real SMTP send to a designated test account under D-08, using the user-provided setup. D-18 requires only the actual send-call result: accepted for sending or a returned error. No retries, uncertain-outcome investigation, resend workflow or verification of actual recipient delivery is required. Local fixtures may demonstrate a returned error but cannot replace the real SMTP example. Templates remain usable for preview when delivery is disabled, and consumers can insert a resolved result without importing the delivery implementation. Actual SMS/WhatsApp/Messenger/Viber integration is outside the default proof scope; examples do not authorize sending.

Expected signal: identical inputs produce an exact expected channel payload; missing/unsafe values are handled predictably; stored definitions survive restart; the example SMTP send reports acceptance or a returned error; unavailable sending leaves preview functional. D-08 keeps real test-account sending and D-18 excludes delivery-reliability machinery from this proof.

## C-03 Form Builder

Target: `proofs/form-builder/`. Human actors: authorized form designer/admin, signed-in respondent and public-link respondent without sign-in, according to the form’s selected mode (D-13). Candidate entities: DraftForm, PublishedFormRevision, FieldDefinition, Response and file reference when file input is supported.

Provide ordered questions and selected-question settings; D-26 removes the previously planned Outline pane. Use the question types in the supplied template as the initial catalogue; document any deliberately excluded or additional type before Freeze. Stable field names/IDs preserve response meaning; duplicate creates a new identity. Drag and move up/down controls yield the same order. Cover settings, validation, preview, publish/status, Responses and Share. Stage-attached forms reuse these definitions and response validation through the authorized card boundary.

Persist a form; submit a valid response and reject invalid/missing required values on the server. Show accessible field errors, successful completion, repeated submit handling, expired/unpublished form and denied access. D-15 requires that edits publish a new immutable revision for new work. Test that a response retains its original revision, field labels/options and meaning after later publication and restart, while a new response started against the new publication records that new revision. Conditional rules, file handling and share-token/access policy need explicit scope decisions if present in the chosen template.

A local file adapter may exercise allowed file types, size limits and storage failure; absence disables the relevant field capability without breaking text questions. D-13 requires both respondent modes: enforce signed-in access on restricted forms and accept anonymous public-link submissions for forms configured for that mode. Enforce the selected mode on the server; public submission must not expose editing endpoints or stored responses. D-14 requires authorized form owners to revoke a public link: reject new submissions through it on the server, including from a page opened before revocation, while retaining the form and existing responses. Reject unauthorized revocation and verify the revoked state survives restart. Other sharing rules remain G-15. Preview is not a stored response; publish must identify the exact revision.

Expected signal: an authorized designer creates/publishes fixture forms in each mode; a signed-in user submits the restricted form, an anonymous user submits through a public link, and unauthorized edits or anonymous restricted-form submissions are rejected; revoking the public link blocks new submissions without deleting its form or responses; response data survives restart and still renders under the correct revision after later edits. D-15 resolves publication/version policy; G-11 retains implementation evidence, and remaining field/share scope stays in G-07/G-15.

## C-04 Chat View

Target: `proofs/chat-view/`. Human actors: conversation operator and permitted collaborator. Candidate entities: Conversation, Participant, Message, InternalNote, AttachmentReference and ActivityEvent. This is a shared conversation view, separate from the agent panel and from the complete Chat product.

Demonstrate conversation list, selected thread and optional details panel; day dividers, attachment states, internal notes, status events, composer and template insertion. Support-style details and Inbox-style two-pane use should be possible by configuration/composition. Apply the common shell's mobile panel and focus contracts. D-19 distinguishes Support-style multichannel chat (email/Messenger/WhatsApp/Viber), which updates live automatically, from email-only use, where periodic/manual refresh is acceptable. Demonstrate both contexts using persisted fixture arrivals; no live social-provider integration is added.

Use persisted fixture conversations, a real outgoing SMTP adapter for the email send path under D-08, and local channel adapters for other fixtures and controlled failures. Exercise draft/send, sending/success/error, empty thread, new message, unread/read state, thread switch, long history and reload/restart. Stable message IDs prevent duplicate display on reconnect. Example sending follows D-18 without a delivery retry/reconciliation requirement. Internal notes are never included in outbound channel payloads; unread counts and conversation access are scoped to the caller.

When Message Templates is disabled, basic composition still works and template controls are absent. When a channel is unavailable, retain reading/drafts and show the send restriction. Display the example send-call result accurately; a local queue entry is not an SMTP acceptance result, and acceptance does not claim recipient delivery. Real outgoing email is required by D-08. Incoming-mail synchronization and live social-network or telephony integrations are not selected; inbound fixture messages do not prove a live receive integration.

Expected signal: permitted operators make real SMTP example sends to designated test accounts and see the call result, use fixture messages to show automatic updates in the multichannel context and periodic/manual refresh in the email-only context, preserve order/history and maintain internal-note separation. Mobile details and the agent panel must not trap focus or produce inaccessible overlapping sheets (G-12).

## Common adoption evidence

Each component must document public service/event contracts, schema/config ownership, safe fixture setup, enabled/disabled/missing-dependency behavior and a consumer integration example. Verify at least one normal path, one permission denial, one validation failure, one dependency failure and restart persistence for its actual responsibility. Test integration through public contracts, not imports into a sibling plugin's private code.

The combined adoption rehearsal moves a fixture card, renders a message, collects a form response and shows a conversation using the same identity/theme shell. It must remain possible to omit each optional component without breaking independent siblings. Browser and data evidence are both required.
