## Boundaries

P-00 is a bounded comparison, not a second application framework rewrite. It must not replace the maintained baseline or authorize a package bump. P-00/P-01 require real OpenRouter model calls under D-07; controlled scripted failures are supplementary. P-01 checks version guidance only for upgrades; D-11 requires a live GitHub Releases check plus local edge-case fixtures, with D-12 faithful section display. D-08 requires real SMTP email to designated test accounts for P-03/P-05 and any email action exercised in P-02. Deterministic local adapters remain for controlled failures and other channel fixtures. No real customer data, customer recipients, unselected live channels or production databases are included. Every proof app represents one company per installation (D-10), while multiple-user permission and account-isolation checks remain required. P-06 is an adoption check rather than another product.

Prioritize uncertainty in P-00 and the identity/rendering bridge before building the full shell. Message-template contracts can then support automation/chat without coupling those plugins. Exact implementation sequencing belongs in tasks/ after Freeze, not in accepted context.

## Receipt contract

For each proof record: source revision/fingerprints, package/runtime pins, fixture identity, commands, start/finish times, expected vs observed assertions, check outcome, browser observations/screenshots, permission/dependency failures, data persistence, cleanup and limitations. For live-model cases also record requested/returned model IDs, provider route when exposed, relevant request settings, per-model action/result evidence, duration and reported usage. Do not silently substitute another model or claim a missing-key run passed. For live-email cases retain the fixture/operation/message correlation, sender/test-recipient identity as appropriate, the actual SMTP call result and any returned error. Keep credentials out of receipts; missing SMTP setup cannot count as a live-send pass. D-18 requires no mailbox receipt check or delivery/retry investigation; an error is reported as the call outcome without claiming the message could not have arrived. For About record GitHub repository/release identity, check time, installed/returned versions, the source “Upgrade Instructions” section and observed rendered/copied content; label fixture runs separately and leave an unavailable live source unrun/failed. For version cases record the old/new definition and revision identifiers, the response/message/run associations before and after publication/restart, unchanged historical meaning and new-work version selection. Keep secrets and live tokens out of receipts. A failing or unrun check is never described as passed.

For current app-shell/common-components work, use the accepted [Yarn and CLI conventions](../../references/00373-stackpress-yarn-cli-and-proof-layout.md): frozen Yarn install, generate, typecheck, build, managed dev/preview/serve and the plugin-importing `yarn test` entry. The 2026-10-08 decision supersedes the original npm/prove command recommendation; earlier execution results retain the commands actually used. Keep schema application separate and restricted to the current run's checked-empty disposable database. Check PostgreSQL explicitly where behavior or claims depend on it.

The final adoption guidance must identify the source revision and what to copy/import, how to modify the copy for an app and rerun its checks, what to configure, built-in Stackpress behavior reused, schemas/migrations, optional dependencies, extension points, verification commands and unproved production concerns. Promote proven reusable findings to context only after review; leave experiment details and failed candidates here.
