# Reusable OfficePress proof guidance

The user wants a set of functional proofs that other OfficePress apps can adopt: an app shell plus Workflows/Automations, Message Templates, Form Builder and Chat View. Each proof must make its configuration, dependencies, source boundaries, verification and adoption steps understandable. A demonstration does not establish production readiness for an adopting app.

The user's 2026-10-05 review clarifies that Automations belong to workflow stages, not a top-level menu item. Keep the automation plugin independent, expose it through the selected stage, and hide its controls if unavailable. Workflow action feedback uses Stackpress's Toastify-backed notifier. Contextual card details use the shell's right-panel layout with independent scrolling, resizing, selected-source toggle/replacement and mobile focus handling; they are not an inset card inside the board. Read [the workflow feedback round](../../proofs/common-components/tests/evidence/reviews/r002-workflow-feedback/notes.md) for the applied corrections and bounded verification.

Use the maintained [Stackpress baseline](stackpress-scaffolding.md), the [shared experience](shared-app-experience.md), [UI source resources](../references/00359-officepress-ui-source-resources.md) and the [current design revision](../references/00360-officepress-about-menu-revision.md). Keep plugins separated by responsibility and verify graceful absence under restart-based selection.

App Settings behavior — the two-tab About/Theme menu, config-owned Agent/Notification settings and faithful display of GitHub release Upgrade Instructions — follows [shared settings guidance](shared-app-experience.md#account-and-app-settings), which owns that decision. Use built-in Stackpress identity/account behavior where verified, and style it to OfficePress. The agent mode references agent-native, but its actual package adoption versus architectural adaptation remains undecided.

Apps initially adopt these proofs by copying documented plugins into their own codebase, then modifying the copies for their use cases. Adoption documentation must explain the copy inputs, dependencies, configuration, schemas and verification steps. The consumer proof must demonstrate independent copying and a use-case modification. This initial adoption path does not require reusable package distribution.

The form-builder proof supports both signed-in and public-link response modes, selected per form. Public links allow submission without signing in; editing remains restricted to authorized users. Public submission does not grant access to editing or stored responses. Authorized form owners can revoke a public share link to stop new submissions through it while preserving the form and existing responses. Enforce revocation on the server, including submissions from an already-open page. Other link lifecycle details and response-viewing roles remain in the spec until resolved.

Workflows start with a list, then open a selected board. The user's 2026-10-06 correction removes workflow versions: save a mutable workflow with a Draft/Published dropdown. Cards can move to any column in that workflow; allowed-next-stage lists, WIP limits and owner/task/document entry requirements are excluded from both forms and server enforcement. Stage labels are “Assignees” and “Tasks”; the later multi-assignee review supersedes the singular label. The board has no workflow selector/count group. Stage Automations places its title/context below the action row and omits statistics and rule search. Read [round 3](../../proofs/common-components/tests/evidence/reviews/r003-workflow-simplification/notes.md) for all 13 corrections, data compatibility and verification; [D-23](../specs/00001-reusable-app-shell-and-component-proofs/decisions.md) supersedes the workflow portion of D-15 and the prior movement restrictions.

Cards and stages support multiple assignees. Board cards show avatars without visible names and an SLA progress bar from current-column entry to expiry when a time target is set; remove the visible Overdue label. Each column has a settings cog before its automation control, opening that stage's settings. Center the stage heading with Automations and keep Automations clickable when tasks are removed or the workflow has unsaved edits. Read [round 4](../../proofs/common-components/tests/evidence/reviews/r004-workflow-assignees-sla/notes.md) for the eight corrections, draft-preserving navigation, compatibility behavior and bounded proof evidence; [D-24](../specs/00001-reusable-app-shell-and-component-proofs/decisions.md) records this later user decision.

The subsequent card-details review labels the checklist “Todo”, places Move to stage below its tasks, and shows a live SLA bar with its due date/time above Files only when the stage SLA is positive. The toolbar uses an arrow-only back control and “Edit”, keeps search and buttons from overlapping as panel width changes, and the workflow designer omits its breadcrumb. Read [round 5](../../proofs/common-components/tests/evidence/reviews/r005-card-details-toolbar/notes.md) for all seven annotations and desktop/mobile verification. The stage designer still labels its task templates “Tasks”.

The next review requires tasks to follow each card's current stage in the backend as well as the UI. Removing a stage task removes its stale checkbox and count from existing cards; an empty checklist has no progress count. Replace the REQUEST/ID caption with the card title, and place its drag grip on the left. [D-25](../specs/00001-reusable-app-shell-and-component-proofs/decisions.md) supersedes the earlier copy-on-entry-only task behavior. Read [round 6](../../proofs/common-components/tests/evidence/reviews/r006-dynamic-stage-tasks/notes.md) for stable task identities, completion retention, legacy adaptation, automation additions and verification.

The next automation review removes Publish and uses a saved Draft/Active/Paused dropdown. Triggers cover card actions: Enter/Exit Stage, Task Checked/Unchecked, File Uploaded, Comment Created/Updated/Removed, Form Submitted when stage forms exist, Title Changed and other supported card actions. Conditions are explicit: Title uses eq/ne/contains/not contains with text; checked/unchecked tasks, submitted/not-submitted forms and uploaded files use eq/ne/gt/gte/lt/lte with numbers; Assigned To uses any/all with a text list. Actions are Check/Uncheck Task, Add/Remove Assignee, Add Comment, Attach File and Send Message using Message Templates and variables. The once-per-visit and stop-on-failure settings are real checkboxes. Stage name/Description span full rows, Outcome sits beside Time target, and Assignees occupies its own row above Tasks without the retention hint. Stage Forms choose Form Builder templates and the section is absent when none exist. Form Builder no longer has an Outline pane. Read [round 7](../../proofs/common-components/tests/evidence/reviews/r007-card-event-automations/notes.md) for all eleven annotations and the backend/provider boundaries; [D-26](../specs/00001-reusable-app-shell-and-component-proofs/decisions.md) supersedes automation publishing in D-15.

Published form and template definitions remain immutable versions. Existing responses and sent messages retain their original definition and meaning. Automation runs retain their original definition/checkpoints, independently of the removed Publish workflow. These unaffected parts of [Q-008 and D-15](../specs/00001-reusable-app-shell-and-component-proofs/decisions.md) remain in force; workflow definition versions are superseded by D-23 and automation publishing by D-26. Internal atomic revision checks prevent stale writes and are not user-facing workflow versions.

The [proof-suite specification](../specs/00001-reusable-app-shell-and-component-proofs/index.md) holds proposed architecture, gaps and proof contracts. It is Planning / Not Frozen. [P-00/P-01 execution results](../specs/00001-reusable-app-shell-and-component-proofs/proof-results.md) record bounded comparison/shell evidence and remaining gaps. The user has approved the app-shell proof as the foundation for a separate [common-components proof](../../proofs/common-components/README.md), with one left-menu item per component. It groups P-02–P-05 into one app and awaits its own manual approval; P-06 remains planned. Approval of the shell preserves its recorded recovery/deletion/provider limitations. Only user-approved rules and later accepted reusable findings belong here; experiment results, failed candidates and sequencing remain spec-local.

The source-backed initial proof rules are elapsed SLA time (entry instant plus duration/deadline) and stale-write rejection with explicit conflict/reload recovery, enforced atomically in adopted operations. [The live-project correlation](../references/00368-officepress-live-project-correlation.md) explains these evidence-resolved rules and routes complete implementation details. Load it before asking further questions or copying components; source-specific versioning, rendering and plugin composition differences remain spec-local until reconciled. Message-template example sends report the real send-call acceptance/error result. Retry handling, investigation of uncertain delivery and recipient-delivery confirmation are outside this proof scope under [D-18](../specs/00001-reusable-app-shell-and-component-proofs/decisions.md); preserve SMTP sending to designated test accounts.

The shared Chat View refreshes according to its use case. Support-style conversations across email, Messenger, WhatsApp and Viber have automatic live updates. Email-only use may refresh periodically or manually. [D-19 and the exact Q-011 answer](../specs/00001-reusable-app-shell-and-component-proofs/questions.md#q-011--visible-chat-and-notification-updates) establish this distinction; adapters/transport remain implementation details. The proof demonstrates both with fixture arrivals, preserving the existing live SMTP example-send boundary. This does not introduce live integrations for the other channels or dictate a global notification cadence.

The user's 2026-10-06 Chat View direction uses the [Inbox r015 messenger wireframe](https://wireframes.blanquera.com/inbox/r015-board-automation-sla/pages/messenger) as the frontend shape while retaining the current OfficePress colors. This is a layout reference, not authorization for new messaging providers or every illustrated wireframe control. Read [round 8](../../proofs/common-components/tests/evidence/reviews/r008-chat-messenger/notes.md) for the compact conversation previews, message bubbles, composer and shell-owned details adaptation with desktop/mobile evidence. The 2026-10-07 correction explicitly requires the reference's Messages and Requests navigation, which round 8 omitted, and edge-to-edge hover/active backgrounds in the left app aside. Read [round 9](../../proofs/common-components/tests/evidence/reviews/r009-message-requests/notes.md) for the applied navigation, persisted request-disposition flow, bounded fixture/provider scope and sidebar verification.

For mobile layout, the shell owns one active overlay for navigation, agent or details. Opening another closes the current one, with focus transfer and clean close/Escape behavior; desktop docked panels keep their existing layout. Follow [shared frame guidance](shared-app-experience.md#frame-and-global-controls) and D-20 when adopting the shell into component proofs.

The initial app-shell proof excludes custom lost-authenticator recovery. Cover existing Stackpress 2FA setup, sign-in and removal with OfficePress styling/integration, and retain normal forgot-password scope. [D-21](../specs/00001-reusable-app-shell-and-component-proofs/decisions.md) is a proof boundary; it neither adds excluded factor methods nor chooses production recovery policy. Current-app user-data purge and across-app account deletion retain their established distinct scopes in [shared settings guidance](shared-app-experience.md#account-and-app-settings); actual tested handler/data coverage and remaining implementation gaps are recorded in the spec-local P-01 results.
